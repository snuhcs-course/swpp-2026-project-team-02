# 진행도 기반 에이전트 재평가

2026-11-28 사용자 요청으로 Live 재평가의 고정 점수 배분을 에이전트 제안 방식으로 변경했다. 최초 생성과 단일 일정 자동 이동 에이전트는 변경하지 않았다. Demo는 네트워크 없는 점수 기반 시뮬레이션이며 Live와 같은 분량을 보장하지 않는다.

## 에이전트 입력과 역할

실제 `ReassessmentAgent`가 OpenRouter의 설정된 모델을 호출하고 `propose_reassessment` 도구로 각 기존 미래 시간대 안의 토픽·분량을 제안한다. 고정 `2-score` 공식으로 결과를 대체하는 fallback은 없다. 입력에는 다음이 들어간다.

- 현재 계획 전체와 변경 가능한 각 구간의 시작·끝·정확한 분량, 보호할 일정 ID.
- 새 진단의 토픽별 정답률.
- 토픽별 현재 계획상의 배정량, 실제 학습 시간, 완료 처리된 계획 분량, 미완료 목표, 변경 가능한 분량.
- 사용자가 입력한 현재 공부 행의 `done/partly/missed` 및 `actual_minutes`.
- 시험일·준비 기간·가용 시간과 남은 총시간.

`done`은 해당 행의 계획 분량을 완료 처리하고, `partly`는 실제 학습 시간만큼 최대 계획 분량까지 반영한다. 실제 분수는 별도 값으로 그대로 전달한다. 기록이 없는 과거 시간은 완료로 추정하지 않는다. 목표량은 현재 계획을 기준으로 계산하며, 최초 생성 때의 불변 목표나 학습 숙련도를 복원했다고 주장하지 않는다.

예를 들어 검증 원본의 매크로는 계획 160분, 실제 학습 140분, 완료 처리된 계획 분량 140분, 미완료 목표 20분이었다. 이를 새 진단 점수와 함께 모델에 전달했다. 재진단에서 약하면 이전 목표를 채웠더라도 복습을 다시 배정할 수 있다. 진단이 100%인 토픽에는 모델이 0분을 배정할 수 있지만, 100% 미만인 취약 토픽을 전부 누락하는 제안은 거절한다.

## 제약과 저장

백엔드는 모델이 바꿀 수 없는 규칙을 검증한다. 보호 행은 ID·시간·토픽을 유지하고 각 변경 대상 구간은 원래 시작부터 끝까지 빈틈·겹침 없이 덮는다. 구간별 분량과 총시간을 보존하며 새 조각은 15분 이상이다. 원래 더 짧은 구간은 더 나누지 않는다. 알 수 없는 토픽·일정 ID, 누락·중복 구간, 취약 토픽 누락, 잘못된 분량은 모델에 구체적인 오류를 돌려주어 수정하게 한다. 최대 4회 요청 내 성공하지 못하거나 제공자가 실패하면 원본을 저장하지 않는다.

확인 저장 시 모델을 다시 호출하면 결과가 달라질 수 있으므로 다음 계약을 사용한다.

1. `commit=false`: 실제 모델 제안을 검증하고 읽기 전용 미리보기와 `preview_token`을 반환한다.
2. 토큰은 현재 계획·메타데이터·진단 점수·학습 기록·제안 행의 해시와 15분 유효기간을 HMAC으로 묶는다.
3. `commit=true`: 같은 입력에 미리보기 전체 행 `previewed_schedules`와 토큰을 보낸다. 서명·입력·현재 시각·동시 수정 여부를 검증하고 그 행만 저장한다. 모델 호출은 0회다.

변조·입력 변경·만료에는 `REASSESSMENT_PREVIEW_EXPIRED`로 다시 미리보기를 요청한다. `APP_REASSESSMENT_SIGNING_KEY`를 프로세스 환경 변수에 설정하면 재시작·여러 워커에서 키를 공유할 수 있다. 미설정 시 프로세스별 임시 키이므로 서버 재시작 후 새 미리보기가 필요하다. 토큰이나 학습 기록을 서버 파일로 저장하지 않는다. 학습 기록은 이번 검토를 위해 백엔드와 모델에 일시 전달되므로 이전의 “항상 기기에만 머문다”는 범위와 다르다.

앱은 기록이 없는/현재 행이 아닌 보관용 기록을 보내지 않는다. 미리보기 토큰은 화면의 제안에만 연결하고 확인할 때 다시 보낸다. 완료 기록과 새 계획은 기존의 복구 게이트 및 원자적 파일 저장 흐름으로 보존한다. 모델의 자유 서술에는 진단 점수를 숙달로 과장한 표현이 관찰되어, 화면에는 검증된 기록 건수·실제 학습량·남은 분량으로 만든 사실 요약만 표시한다. 원문 설명은 도구 제안 trace에만 남는다.

## 실제 모델 검증

검증용 입력으로 실제 생성한 960분 계획을 사용했다. 고정 시각 12/2 18:10에 과거·진행 중 360분을 보존하고 남은 600분을 각각 독립 재평가했다. 이번 최종 실행은 앞서 실제 모델로 생성해 캡처한 동일 CSV를 격리 저장소에 복원했고, 재평가 제안은 `google/gemini-2.5-flash`를 A/B 각각 실제 1회 호출했다. 확인 저장에는 추가 호출이 없었다.

| 토픽 | 원본 남은 분량 | A: 앞 4개 취약 | B: 뒤 4개 취약 |
| --- | ---: | ---: | ---: |
| 매크로 활용 | 0 | 180 | 0 |
| 스프레드시트 기본 | 0 | 140 | 0 |
| 인터넷 자료 활용 | 40 | 160 | 0 |
| 차트와 분석 | 80 | 120 | 0 |
| 컴퓨터 시스템 보호 | 160 | 0 | 200 |
| 컴퓨터 시스템 활용 | 80 | 0 | 80 |
| 페이지 설정과 인쇄 | 160 | 0 | 160 |
| 함수와 데이터 관리 | 80 | 0 | 160 |
| 합계 | 600 | 600 | 600 |

이 수치는 고정된 정답이나 최적 분량이 아니라 이번 모델의 제안이다. 진행도와 진단 정보를 모델에 전달하고 활용할 수 있는 경로 및 제약을 검증했으며, 반복 실행의 동일 결과나 학습 효과의 향상을 입증한 것은 아니다.

두 경우 모두 새 15분 미만 세션 0개, 최소 세션 40분이었다. 각 원본 시간대·보호 행·메타데이터를 유지했고 미리보기·저장·인증된 실제 GET 재조회·CSV가 일치했다. 실제 API 캡처를 Live Repository에 HTTP로 재생하여 ViewModel과 실제 AtomicFile 저장소를 거친 뒤 새 저장소/ViewModel에서도 완료 120분·부분 완료 20분 기록과 변경된 계획이 유지되는지 검증했다. 앱 검증은 캡처 재생 테스트이며 에뮬레이터 UI 조작은 아니다.

초기 실제 모델 실행에서 취약 토픽 누락이 관찰돼 취약 토픽 coverage 검증을 추가했고, 이어진 4회 수정 실패 실행에서는 원본 무변경·502 종료를 확인했다. 구간별 분량·필수 토픽을 명시하고 구체적인 오류를 제공한 뒤 위 실행이 통과했다. 실패를 고정 배분으로 대체하거나 성공으로 집계하지 않았다.

## 테스트와 재현

- Windows: 계획 생성 149개, 일정 조정 94개, API 270개 통과 (API 권한 항목 7개 생략). 마지막 사실 요약 수정은 해당 HTTP 저장 테스트로 추가 확인했다.
- Linux Python 3.12: 위 백엔드 513개가 모두 통과했고 생략은 없었다. 마지막 사실 요약 문구 추가 전의 기능 검증이며 배분·서명 로직은 같다.
- Windows JDK 25: Demo·Live 전체 단위 테스트 성공. 최종 실제 모델 캡처로 양쪽 `GeneratedPlanReassessmentTest`를 추가 실행해 성공했다.
- Demo·Live debug APK 빌드 및 lint 성공.

`backend/`에서 새 실제 실행은 다음과 같다 (모델 사용량 발생).

```powershell
python scenarios/run_generated_plan_reassessment.py `
  --output coverage-results/agent-progress-validation.json `
  --credential-backend ../../repo/backend `
  --fixture-output tests/schedule_adjuster_tests/fixtures/generated_plan_reassessment.json
```

이미 캡처한 실제 생성 결과를 재사용하려면 `--reuse-generation coverage-results/agent-generated-plan-reassessment-generation.json`을 추가한다. 재평가 모델 호출은 그대로 실행된다. 자격 증명 내용은 출력·캡처하지 않는다.

고정 캡처는 `backend/tests/schedule_adjuster_tests/fixtures/generated_plan_reassessment.json`이다. 오프라인 테스트의 모델 응답 대체는 테스트에만 존재하며 제품 fallback이 아니다. 로컬 증빙은 `backend/coverage-results/agent-progress-validation.json`, `agent-android-all-tests.log`, `agent-android-final-checks.log`, `agent-all-api-tests.log`, `agent-adjuster-all-tests.log`, `linux-*_tests.log`에 있다. 새 CI나 서버 배포 결과는 아니다.
