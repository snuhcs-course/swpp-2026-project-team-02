## 3. 현재 구현과 Task 3의 측정 대상

Live 경로는 `POST /api/v1/study-plans → build_plan_request → GeminiToolAgent → PlannerTools → generate_schedule → JSON/CSV 저장`이다. frontend에서 로컬 채점한 `assessment_results`를 보내고, Gemini가 각 문항을 고정 3토픽에 가중치로 분류한다. 자기평가는 자유 문장이다. 현재 Live 구현은 beginner/advanced 같은 고정 레벨 배수로 공부량을 정하지 않는다. fixture의 `expected_level`은 성능 판단 기준으로 사용하지 않는다. Android의 기기 내 `DemoPlanner`는 이번 측정 범위에서 제외했으며 Live와 결과를 섞지 않았다.

현재 backend는 날짜별 용량·일정 충돌을 검사하지만, 기간 전체의 균등화나 저득점 과목에 더 많은 분수를 배정하는 것을 강제하지 않는다. 이 두 요구는 모델 프롬프트에 있다. 기본 통신 제한은 요청당 45초, Agent 최대 6루프이며 앱 전체 호출 제한은 120초다. 6×45초는 단순한 상한 구성 설명이며 실제 생성 시간 측정값이 아니다. 네트워크·도구 처리 등의 추가 시간이 있을 수 있다.

## 4. 지표 정의와 반복 설계

### 시간창별 공부 비율의 모집단 표준편차

관측 단위는 **날짜에 펼친 입력 가용 시간창 하나**다. 준비 시작·시험 종료 시각으로 자르고, 외부 일정의 합집합을 차감한다. 외부 일정 때문에 나뉜 조각은 원래 시간창에 다시 합산하여 일정이 많은 날의 관측 비중이 커지지 않게 한다. 구간은 `[시작, 종료)`다.

입력 일정 시각에는 시간대 정보가 없으므로 이 실험은 KST 일정으로 해석한다. 기존4케이스의 시작일10/05는 검사일10/14보다 앞서 있지만, 버전 재현을 위해 원래 입력을 유지했다. 따라서 기존 케이스는 지정 기간 전체 계획을 평가하며 “지금부터 미래 일정만 생성”하는 평가가 아니다. 통제된 추가 케이스는10/19부터 시작한다.

각 시간창의 순 가용 분수를 `Aᵢ`, 그 안에서 공부 일정이 차지한 분수를 `Sᵢ`라고 두고 `rᵢ=Sᵢ/Aᵢ`를 계산한다. `Aᵢ>0`인 **모든** 창을 포함하며 공부가 없는 창의 비율은 0이다. `Aᵢ=0`인 창은 제외하고 개수를 기록한다.

`σ = sqrt(Σ(rᵢ−r̄)²/N)` — 모집단 표준편차, 비율 단위. 100을 곱하면 퍼센트포인트다. 창이 하나면 σ=0이며 균등성을 판단하기 어렵다. 가용 시간창이 없으면 N/A다. 중복 공부 일정이 있으면 비율·이용률은 공부 구간 합집합으로 계산하고 겹침을 별도 위반으로 기록한다. 총 공부 분수는 원본 공부 행 소요 시간의 합이다.

균등화의 해석에는 전체 이용률 `ΣSᵢ/ΣAᵢ`와 총 공부 분수가 필요하다. 빈 계획도 σ=0이 될 수 있으므로 `empty_study_plan`과 제약 유효성을 함께 본다. 낮은 σ만으로 우수하다고 판정하지 않는다.

### 과목 정답률과 배정 공부 분수의 Pearson

문항 `q`의 배점을 `p_q`, 정오를 `c_q∈{0,1}`, 과목 가중치를 `w_qt`로 두면 `B_t=Σp_qw_qt`, `E_t=Σp_qc_qw_qt`, `P_t=E_t/B_t`다. `M_t`는 해당 과목의 모든 `study-` 행 소요 시간(분)의 합이다. 외부 일정은 공부량에서 제외한다.

`r = Σ(P_t−P̄)(M_t−M̄) / sqrt(Σ(P_t−P̄)² × Σ(M_t−M̄)²)`

`B_t>0`인 과목만 포함하고 진단된 과목에 공부가 없으면 `M_t=0`으로 넣는다. 진단되지 않은 과목의 정답률을 0으로 만들지 않는다. 평가 과목이 2개 미만이거나 정답률 또는 공부 분수 분산이 0이면 N/A로 남긴다. 모든 문항 정답/오답 케이스는 통상 정답률 분산이 0이라 상관계수 대신 총량·분포·성공률을 비교한다.

저득점 과목 우선 학습 목적에는 음의 r을 기대한다. 과목 3개에 대한 r은 탐색적 지표이며 통계적 유의성·모집단 효과를 주장할 자료가 아니다. 기존 5문항의 같은 취약 패턴에서 고득점 두 과목이 동률인 점도 해석 범위를 좁힌다.

측정 도구는 원래 도구/Agent 실행을 그대로 호출하는 관측 래퍼를 사용한다. **성공한 build 호출 당시**의 `topic_statistics`를 저장하므로 실패한 분석 재시도를 마지막 분석이라고 잘못 채택하지 않는다. 입력 fixture의 고정 과목 분류를 이용한 독립 Pearson도 계산한다. 고정 분류는 실험용 기준이며 모델 분류나 공식 시험 과목과 동일하다고 가정하지 않는다. 두 평가가 다르면 배정뿐 아니라 분류 변동도 조사한다.

## 7. 진단 5문항의 과목 편향과 문항 추가

[문제은행](https://github.com/snuhcs-course/swpp-2026-project-team-02/blob/d706ad2ea66aaed6faeebea1c21dc358ace0ecf2/backend/assessment_questionnaire/questions.json)의 고정 라벨은 기본2개(40%), 함수/데이터 관리2개(40%), 차트/분석1개(20%)다. 기본·함수 정답률은 0/50/100%인 반면 차트는0/100%만 가능해 한 번의 오답이 과목 전체 취약도에 매우 크게 반영된다. 질문 하나의 난이도·모호성·우연 정답과 과목 능력을 분리하기 어렵다. 단순 정답률 정규화만으로 이 정보량 차이가 사라지지 않는다.

문항1 절대참조, 2 SUM, 3 IF, 4 원형차트, 5 자동필터의 좁은 내용 범위다. 자동필터는 데이터 관리 지식이기도 해서 기본으로만 라벨링한 기준은 검토가 필요하다. Live는 원문을 보고 분류하므로 고정 fixture의 2·2·1과 다른 가중 분류를 할 수 있다. 따라서 모델 분류의 실행 간 변동과 고정 분류 Pearson을 함께 본다. 제품의 3토픽은 로컬 분류이며 공식 시험 과목 대표성을 검증한 결과가 아니다.

별도 `question_bank_15_draft.json`에 **새 문항10개**를 더해 기본5·함수5·차트5로 균형을 맞췄다. 기존 문항 복제는 하지 않았다. 문항 추가 케이스도 입력 형식과 고정 분류 검증을 통과했다. 이것은 실험용 초안이며 공식 기출·전문가 검토·난이도 보정·진단 신뢰도 검증을 거친 문제은행이 아니다. 차트 추가 문항 상당수도 선택형 개념 문제라 분석 능력을 충분히 측정한다고 단정할 수 없다.

우선 팀이 각 문항의 정답·주제·중복·난이도를 검토하고 실제 대상 사용자에게 예비 평가하여 문항별 정답률과 변별력을 확인해야 한다. 5문항/과목은 비교 실험을 시작하는 수치이며 충분 문항 수를 입증한 기준이 아니다. 15문항이면 고정 단일 라벨에서 정답률 해상도가20%로 같아지지만 실제 품질 검증은 별도다. 향후 중간 점수·혼합 난이도 패턴도 넣어 Pearson 해석을 보완한다.

## 8. 사용자가 완료/실패를 지속적으로 확인하는 방법과 Task 2 연결

현 PlanScreen은 표시 중심이며 on-track/calendar export를 backing data가 없어 제외한다고 명시한다. API에도 사용자별 계획 수행 상태·부분 수행 분수·버전 이력 계약이 없다. 아래는 **미구현 개선 제안**이다.

1. 계획마다 `plan_id`, 버전, 시험일, 사용자별 가용 시간을 저장한다. 일정 식별자는 `(plan_id, schedule_id)`로 묶는다. 지금처럼 생성별로 반복될 수 있는 `study-1`만 전역 ID로 쓰면 다른 계획 상태가 섞인다.
2. 상태를 미착수 / 완료 / 부분 수행 / 실패 / 미확인으로 구분하고 실제 공부 분수·실패 이유·기록 시각을 저장한다. 답변이 없으면 미확인으로 두고 실패를 자동 확정하지 않는다. 앱 재시작 뒤에도 복원한다.
3. 종료 후 사용자 설정 시각에 확인을 요청하고, 일/주 화면에 미완료·미확인 목록을 보여준다. 매일 알림의 시각·빈도는 사용자가 선택한다. 완료율은 확인된 기록의 비율과 미확인 수를 함께 표시한다.
4. 실패·부분 수행 항목에서 “남은 공부 다시 배치”를 선택한다. 실제 수행 분수는 유지하고 미수행 분수만 조정 후보로 만든다. 현 Task 2는 전체 원래 길이를 옮기므로 부분 수행을 그대로 전달하면 공부량을 과다 배정할 수 있다.
5. Task 2 호출 전에 현재 버전 전체 일정과 최신 사용자 가용 시간·시험일·현재 시각을 확보한다. 현재 endpoint는 `schedule_id`와 `schedules`를 받으며 가용 시간은 서버 공용 저장 프로필을 읽는다. 생성 요청의 가용 시간과 조정 프로필이 다를 수 있으므로 계획별 가용 시간 계약이 필요하다.
6. 이동 제안은 남은 분수 보존, 다른 일정 충돌 없음, 가용 시간 준수, 시험일 이전 조건을 검증한다. 전체 길이가 한 창에 못 들어가면 명시적인 세션 분할 제안이나 용량 부족을 제공한다.
7. 사용자가 변경 내용을 확인해 적용할 때 버전을 검사하고 상태/일정/조정 이력을 한 번에 저장한다. 같은 요청의 중복 적용을 막는 request ID를 사용한다. 원래 실패 기록을 지우지 않고 새 시도에 연결한다. 완료한 일정은 재조정 대상으로 제외한다.

제안 데이터/수용 기준은 `개선안_우선순위.csv`에 정리했다. Task 1은 기록·확인 UI, Task 2는 남은 분수·시험일·버전·분할 계약, Task 3은 전후 지표·누적 실패 이유 분석을 담당할 수 있다. 실제 사용자 알림이나 자동 감시는 이번에 설정하지 않았다.
