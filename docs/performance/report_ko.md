3 지표 해석과 성능 병목

지표의 정확한 의미

시간창 j의 가용 분수 A와 그 안의 학습 일정 합집합 분수 U의 비율 U/A를 구하고, A가 0보다 큰 모든 시간창 비율의 모집단 표준편차를 계산한 값이 time_ratio_population_std다. 사용하지 않은 유효 시간창의 비율 0도 포함한다. 0용량 창은 제외한다. Std가 낮아도 공부량이 부족할 수 있어 활용률·학습 분량과 함께 평가해야 한다.

utilization은 실제 가용 구간 합집합 안의 학습 일정 합집합 분수를 전체 가용 분수로 나눈 값이다. 겹치는 바쁜 일정은 합쳐 제외한다. Pearson은 과목별 정답률과 배정 학습 분수 사이의 상관이다. 분산이 없으면 계산하지 않는다. 음수는 취약 과목에 더 많은 시간을 배정하는 경향을 뜻하며 학습 효과를 직접 입증하지 않는다.

constraint_valid는 학습 간 겹침, 바쁜 일정 충돌, 가용 구간 이탈, 잘못된 길이, 중복 ID, 미평가 과목 학습, 빈 학습 계획이 모두 없는지를 판정한다. 성공 77/77회가 통과했으나 이 검사는 균등 배분·취약 과목 우선 배정의 최적성까지 보장하지 않는다.

실패를 포함한 HTTP 소요 시간

| 범위 | n | 평균 초 | 중앙값 초 | p95 초 | 최대 초 |
| --- | --- | --- | --- | --- | --- |
| 전체 | 85 | 5.65 | 5.30 | 7.30 | 18.29 |
| 성공 | 77 | 5.53 | 5.12 | 7.25 | 18.29 |
| 실패 | 8 | 6.82 | 6.23 | 8.91 | 8.91 |

p95는 정렬한 n개 값에서 ceil(0.95×n)번째 값이다. 120초 초과는 0회다. 최장 실행은 Paid_Repeat5 run02의 성공으로 18.29초이며 모델 요청은 6회였다. 폴더 시작 시각 사이의 사용자 대기 시간은 위 측정에 포함하지 않는다.

관측된 지연은 모델 호출 구간에 집중

모델 요청은 성공 실행에서 339회, 실패 실행에서 48회로 총 387회이며 계획 생성당 평균 4.55회다. raw.json의 모델 메서드 누적 시간은 477.56초, 도구 메서드 310회 누적 시간은 0.225초, 전체 HTTP 누적 시간은 480.22초다. 모델 메서드 구간이 HTTP 시간의 약 99.4%를 차지해 호출 횟수와 반복을 줄이는 개선을 우선 검토할 근거가 된다.

모델 메서드 시간에는 외부 통신과 메서드 내부 처리도 포함될 수 있다. 순수 모델 추론 시간이나 비용으로 환산하지 않았으며 토큰·청구 금액 자료는 없다.

8회 모두 요청 6회 후 max_steps=6으로 끝났다. Tiny_Capacity는 10월 19일 18:00~18:01의 1분만 허용한다. trace는 평가 과목을 모두 포함하고 각 분량은 양의 정수여야 한다는 조건과 용량 오류를 보여준다. 관측된 3과목 조건을 동시에 충족하려면 최소 3분이 필요하므로 1분과 양립하기 어렵다는 해석이다. backend 내부 로직은 소스 확보 후 최종 대조해야 한다.

모델 호출 전에 총 가용량과 날짜별 용량, 필수 과목 수·최소 분량을 검사한다. 불가능하면 모델 재시도 대신 시간 추가, 시험일 조정, 목표 축소 선택지를 반환한다. 잘못된 날짜·누락 과목·남은 용량은 구조화된 오류로 전달하고 같은 조건을 바꾸지 않는 반복 호출은 종료한다.

C5 Basic run02와 Overlapping_Busy run05는 마지막 build_study_schedule의 채택 통계가 존재한다. 유효 계획 생성과 최종 응답 완성을 분리해 살피고, 마지막 단계에서 도구가 성공해도 후속 응답 단계가 남지 않는 경로를 점검해야 한다. 단계 한도만 늘리면 추가 지연·요청이 생길 수 있어 성공 직후 종료 규칙과 함께 평가한다.

모델 분류 기준과 고정 분류 기준을 함께 평가

두 Pearson 값이 다른 실행은 10회다. C5 Basic의 r 평균은 모델 기준 -0.892, 고정 기준 -0.725이고 C15 Basic은 -0.945와 -0.920이다. 문항을 분류하는 모델의 결과로 같은 계획을 평가하면 고정 과목 기준과 다른 평가가 나올 수 있다. 비교 실험에서는 고정 분류 지표를 함께 보고 문항 분류 정확도도 별도로 확인한다.

관측 결과를 재현하는 단기 목표와 제품 개선 목표를 구분한다. 불가 안내를 새 정상 처리 범주로 넣으면 기존 success 77/85와 직접 비교하지 말고 valid_plan, infeasible_explained, system_failure 등 별도 결과로 보고한다. 개선 후 효과는 아직 측정하지 않았다.

5 사용자 확인과 재계획 흐름

사용자의 미완료와 시스템 오류를 구분해 기록하고, 남은 분량과 최신 가용 시간을 바탕으로 계획을 조정하는 흐름을 제안한다. 다음 내용은 제품 개선안이며 이번 85회 실험에서 사용자 지속 이용 효과를 측정한 결과는 아니다.

일정 체크와 실제 수행 기록

일정마다 날짜, 과목, 예정 시간·분량을 보여주고 예정, 진행 중, 완료, 부분 완료, 미완료, 건너뜀을 선택하게 한다. 실제 시간과 완료 분량을 남기고 체크를 취소·수정할 수 있게 한다. 날짜가 지났지만 확인하지 않은 일정은 미확인으로 두어 미완료와 구분한다. 시스템이 계획 생성에 실패한 건은 사용자의 미완료에 포함하지 않는다.

미완료 사유와 정기 확인

미완료·부분 완료에는 시간 부족, 예상보다 높은 난이도, 피로, 개인 일정, 계획 과다, 기타 사유를 선택하게 한다. 메모는 선택 사항으로 둔다. 매일 사용자가 정한 시각에 오늘 일정을 확인하고, 주 1회 다음 주 가용 시간과 이월 분량을 검토하도록 제안한다. 알림 시각 변경과 끄기를 제공한다.

사유를 반영한 재계획

남은 분량을 집계하고 수정된 가용량으로 다시 배치한다. 시간 부족이 반복되면 일일 분량 축소·기간 연장을, 난이도 문제에는 단위 분량 축소·복습 시간 추가를 제안한다. 이월 분량이 가용량을 넘으면 자동으로 밀어 넣지 말고 목표 조정을 안내한다. 사용자가 변경 전후 일정과 마감 영향을 확인한 뒤 적용하도록 한다.

| 기록 항목 | 활용 |
| --- | --- |
| plan_id, task_id, version | 원래 계획과 수정 이력 연결 |
| 상태, 예정·실제 시간, 완료 분량 | 진행률과 남은 작업 계산 |
| 사유, 선택 메모, 확인 시각 | 반복 원인과 확인 누락 파악 |
| 조정 사유, 변경 전후, 적용 시각 | 사용자 확인과 변경 이력 관리 |

도입 후 확인률, 완료율, 사유 기록률, 재계획 수락률, 이월량을 기간별로 측정한다. 반복 알림이 부담이 되지 않도록 빈도를 조절하고 학습 기록·개인 메모의 보관 기간과 삭제 기능을 제공한다.

6 개선 우선순위와 검증 기준

| 우선 | 개선 항목 | 기대 효과와 확인 기준 |
| --- | --- | --- |
| P0 | 가용량·필수 과목 사전 검사 | tiny 5회 모두 명시적 불가 안내 또는 정의된 정상 결과 |
| P0 | 도구 성공 후 종료, 반복 오류 제한 | 마지막 build 수용 후 단계 초과 해소, 요청 수 감소 |
| P1 | 과목·날짜·오류 구조화와 결정적 배치 | 동일 입력에서 제약 통과 유지, 모델 요청 감소 |
| P1 | 고정 분류 기준 품질 평가 | 분류 변화와 시간 배분 효과를 분리해 비교 |
| P1 | 일정 체크·사유·주간 확인 | 미확인과 미완료 구분, 사용자 흐름 검증 |
| P2 | 사유 기반 재계획과 알림 조정 | 가용량 초과 이월 방지, 장기 완료율 측정 |

위 기준은 제안이며 개선 후 달성값이 아니다. 비교 시 입력·반복 수·모델·프롬프트·커밋을 고정하고 변경점을 기록한다. 단계 한도나 모델을 바꾸면 지연·요청 수·정상 처리율을 함께 비교한다. 같은 입력의 5회 반복은 탐색적 결과이며 실제 사용자나 다양한 시험 환경 전체를 대표하지 않는다.

기존 offline 검사도 함께 제출

원본 offline 로그에는 입력 17개 유효, 지표 산술 테스트 9개 통과, schedule_adjuster 테스트 15개 통과가 기록돼 있다. license_planner 테스트는 13개 중 12개 통과·1개 실패다. 실패는 weekly_availability 저장의 7요일 정규화와 테스트의 2요일 기대값 차이로 보이며 수정 완료 증거는 없다. 현재 backend 전체 테스트가 통과했다고 보고하지 않는다.

이번 보완에서는 공급된 산술 테스트 9개를 다시 실행해 모두 통과했다. backend 소스가 없어 기존 backend 테스트와 scripted 검사는 다시 실행하지 않았다. 원본에 있는 2개 harness 합성 테스트의 로그는 보존했지만 대응 소스 파일이 없어 해당 2개 검사의 재실행은 별도 보완이 필요하다.

offline 예시는 live 성능과 구분

사람이 정한 동일 90분 배정을 집중·분산한 scripted 기록은 활용률이 모두 12.5%여도 Std가 0.280과 0으로 달랐다. 강한 과목에 더 많은 시간을 준 예시는 r=+1인데도 backend가 수용했다. 이는 지표들이 서로 다른 속성을 측정하며 제약 통과만으로 취약도 배분을 보장하지 않음을 보여주는 보조 근거다. 이 값은 Gemini 성능 표에 합산하지 않았다.

7 팀원 재현 방법과 제출 상태

제출 파일과 실행 순서

ZIP에는 원본 624파일, 실행용 task3 폴더, 17개 case_id 목록, 재집계 결과·검증 도구, README·재현 도우미·requirements·체크리스트·해시를 담았다. 원본 스크립트·입력의 실행용 사본은 원본과 바이트가 같다. 과거 offline 문서의 live 0회 표현은 원본 보존용이며 최종 결과는 이 보고서와 루트 README를 기준으로 한다.

① Python으로 task3/test_metrics.py를 실행한다. ② aggregate_results.py --out recheck-01로 API 호출 없이 원본 결과를 검증한다. ③ README의 저장소 URL에서 별도 사본을 받아 지정 커밋으로 고정한다. ④ 원 실험의 Python 3.14.7과 backend 설정을 확인한다. ⑤ offline 확인 후 각자의 GEMINI_API_KEY로 케이스별 5회 live를 실행한다. ⑥ 새 결과는 original을 덮어쓰지 않고 별도 경로에 저장한다.

기본 재현 도우미는 17개 케이스를 각각 별도 프로세스에서 seed 20261014로 실행한다. 원 측정기에서 case_id를 생략하고 전체를 한 번에 실행할 수도 있지만 실행 순서 조건이 달라진다. seed는 순서만 고정하며 모델 응답을 결정적으로 만들지는 않는다. 측정기가 로컬 서버를 시작·종료하므로 별도 서버 실행은 필요 없다.

재실행에 필요한 누락 및 별도 준비

| 항목 | 상태와 필요한 조치 |
| --- | --- |
| 고정 커밋 backend 소스 | ZIP에 없음. 저장소 접근권한 또는 전체 소스 사본 필요 |
| backend 기존 테스트와 fixture | ZIP에 없음. 같은 커밋의 테스트 디렉터리 필요 |
| 개인 API 키·모델 권한 | 의도적으로 미포함. 각 팀원이 발급·설정 |
| 과거 합성 테스트 2개의 코드 | 로그만 있음. 그 검사 자체를 재현하려면 코드 추가 |
| backend 의존성·설정 전문 | 원 가이드는 외부 패키지 없음으로 기록. 소스 확보 후 대조 |

실패 8회에 성공용 metrics·schedule 파일이 없는 것은 정상이다. 측정기는 표준 라이브러리 전용이므로 requirements에 추정 패키지를 넣지 않았다. API 키·.env·인증 파일은 포함하지 않았으며 토큰·비용 수치도 만들지 않았다.
